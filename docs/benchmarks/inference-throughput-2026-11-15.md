# 跨平台推理与吞吐优化调查

2026-11-15。基线为 MTranServer 5.2.1，提交 `3a02b390e6c1f22f1a3c500dc173d72398f45cfa`。本轮只做隔离实验，生产代码未改，没有候选作为通用默认后端合入。

## 结论

借鉴 vLLM 的跨请求合批和调度思路能改善特定设备高负载吞吐，但收益不能跨平台直接推广。ONNX Runtime 计算核心已经是原生实现，改用 C、Zig 或 Rust 本身不保证更快。统一接口和模型逻辑可以复用，SIMD、量化、GPU 内核、内存布局及打包仍需分别适配。

优先保留现有后端，继续研究经设备和负载校准的调度策略；本轮证据不足以支持从零重写通用引擎。

## 测试范围

- 同一中英双向 SSRU 翻译模型；本地 x86 CPU、M4 CPU/Metal/WebGPU、Thor SM110 CPU/CUDA。
- 真实 HTTP 候选保留现有分词、分句、递归切分和占位符流程；缓存关闭，两个轮换顺序的测试轮次。
- 每方向64个不同参考句子及64个文档请求；每个文档拼接8句。并发1/2/4/8/16/32，记录吞吐、P50/P95/P99和进程树RSS。
- 组件测试、token输入HTTP测试与完整服务测试分别记录，不能互相替代。这里的8句文档不能与此前32句长文成绩直接比较。

## ONNX 跨请求合批

原生异步候选共享一个ORT会话，最多4个同时运行的批次，每次运行1个CPU线程。下表为32并发、两轮吞吐中位数，单位请求/秒。

| 设备 | 场景 | Fast CPU | 合批候选 |
| --- | --- | ---: | ---: |
| M4 | 英→中单句 | 272.33 | 358.50 |
| M4 | 中→英单句 | 251.00 | 362.15 |
| M4 | 英→中文档 | 34.11 | 45.36 |
| M4 | 中→英文档 | 28.51 | 48.76 |
| x86 | 英→中单句 | 219.77 | 188.69 |
| x86 | 中→英单句 | 222.05 | 206.04 |
| x86 | 英→中文档 | 29.13 | 23.84 |
| x86 | 中→英文档 | 21.79 | 19.04 |
| Thor | 英→中单句 | 189.14 | 178.53 |
| Thor | 中→英单句 | 175.40 | 181.45 |
| Thor | 英→中文档 | 23.33 | 23.14 |
| Thor | 中→英文档 | 30.20 | 26.29 |

M4吞吐提高约32%–71%，中→英文档P95从1201ms降至749ms。但低并发明显退化，x86没有同样收益，Thor多数场景无收益。

另测按待处理请求数切换的策略：低于16走原路径，高负载启用合批。M4上低负载接近基线，但32并发单句吞吐英→中277→238、中→英255→212，文档则改善。该策略包含惰性初始化与路径切换，未单独消融，不能断言退化只由初始化造成；未采用为默认策略。

## 各方向验收

| 方向 | 已完成的验证 | 决策 |
| --- | --- | --- |
| 合批、长度分组、token预算 | batch1/2/4/8/16/32分组对照；128/256/512/1024填充源token预算与batch1/4/8/16/32共40个FP32场景 | 输出验证通过；不是解码token预算；收益依赖设备与负载 |
| EOS退出、请求补位 | 真正到达时编码、独立候选表与循环状态、完成立即返回、队列取消 | 当前CPU状态搬运和候选表重组使在线补位慢于整批排空，拒绝当前实现 |
| 设备常驻、固定形状捕获 | 原生C API、GPU缓冲区、固定地址、正确初始化INT64选项、完整输出核对 | WebGPU完整4句组件耗时仍高于CPU；不作为HTTP加速成果 |
| 小算子融合 | 归一化融合及保留的注意力融合对照 | 注意力对照逐行验证EOS并比较完整截断token，但属于旧组件实验；未形成通用收益 |
| GenAI分页注意力 | 编译未修改的上游模型状态验证器 | fixed_recurrent配置有效，但动态Engine要求恰好一个paged_kv组，纯SSRU不能直接接入 |
| 前缀缓存 | 两方向追加后缀，检查共享前缀cross-attention状态 | 状态发生变化，双向编码器不支持直接复用独立源前缀 |
| ggml | 相同模型CPU、Metal、CUDA适配；独立质量及真实HTTP进程池 | 没有稳定超越现有Fast的吞吐 |
| CTranslate2 | 官方转换器兼容性检查、自定义native-ops SSRU CPU/MPS适配、质量及HTTP进程池 | 官方转换器拒绝当前SSRU；自定义适配不是官方Translator，多数场景无优势 |

分页KV主要解决增长的自回归历史；当前SSRU每请求固定循环状态约6144字节（FP32），不能机械套用LLM的缓存方案。

## 原生后端与质量

原生进程池为4个worker。x86的CT2 INT8中→英文档32并发约24.3rps，相同轮次CPU约21.8rps，存在局部收益，但其他多数场景落后。M4原生适配多数落后；Thor ggml CUDA单请求可有收益，高并发吞吐仍明显低于当前CPU。

进程树峰值RSS：x86 CPU约857MiB，CT2约2468MiB、ggml约2406MiB；M4 CPU约1104MiB，CT2约2971MiB、ggml约4283MiB。它们是跨进程RSS相加，不能当成去重后的物理内存。

独立质量检查已覆盖改变输出的候选。组件质量集为双向、普通/Fast合计800条预测，重复运行检查确定性；HTTP质量每方向64个独立参考句子，重复轮次不是新增独立样本。CT2 MPS的800条预测token与FP32参考一致；量化合批及其他量化后端存在译文变化，均值接近也有专有名词、语义等实际退化，不能称无损。

## 可靠性与平台边界

原型通过畸形批次/掩码、调用方修改提交缓冲、运行中关闭、崩溃与截断响应、排队断开、过载拒绝及恢复检查。三台机器都做了进程/模型冷启动；未清OS和驱动缓存。这些检查不代表生产已有通用过载保护或长期稳定性验收。

ggml实际验证CPU/Metal/CUDA；其他后端的源码构建入口不等于设备验收。CT2实际验证CPU/MPS，未测其NVIDIA/ROCm适配器；ARM CUDA需要单独构建。未验证浏览器、手机或Windows真机，也未做长期满载。不能把这些适配器的结果解释为框架性能上限。
