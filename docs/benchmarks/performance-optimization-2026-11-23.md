# 普通与 Fast 双模式深度性能优化与全链路 ABBA 实测报告（2026-11-23）

本报告记录在 `v5.4.6`（基线提交 `bde0f20`）基础上针对 ONNX 普通模式（`--no-fast`）与 Fast 模式（`--fast`）开展的四轮（Waves 1–4）系统优化、跨平台/WASM 兼容验收以及三轮严格交替 ABBA 基准测试（候选提交 `b711a71`）。全部结构化基准与兼容数据见 [performance-optimization-2026-11-23.json](performance-optimization-2026-11-23.json)。后续在提交 `299ece2` 增加 Linux cgroup CPU 配额感知后，于 `AMD Ryzen 9 9950X`（4 CPU 配额、3 GiB 内存）完成的同口径与 LinguaSpark 三方对比实测见 [cpu-comparison-2026-11-23.md](cpu-comparison-2026-11-23.md)。

## 测试环境

- **主机硬件**：Intel Core i5-14400（6 P-core / 12 逻辑核 + 4 E-core，共 16 线程，20 MiB L3，支持 AVX2 / AVX-VNNI）
- **运行环境**：`linux-x64`，Node `v26.13.1`，ONNX Runtime `1.30.0`，`MT_CPU_ONLY=true`，`cacheSize=0`，关闭标点转换与日志落盘
- **模型与语料**：Mozilla `en_zh-Hans` 与 `zh-Hans_en` 双向模型；HTTP 语料包含 27 条输入（10 英中短句、3 英中段落、1 英中长文 32 句/3244 字符、10 中英短句、2 中英段落、1 中英长文 32 句/1516 字符）
- **测试方法**：将 `bde0f20` 与 `b711a71` 在干净工作树下逐轮交替执行（round 0 baseline→candidate，round 1 candidate→baseline，round 2 baseline→candidate），所有吞吐与延迟指标取 3 轮各自中位数

## 核心优化架构（Waves 1–4）

1. **图结构与本地原生编码/解码全栈打通**：
   - 新增紧凑 INT8 自定义算子 `com.mtran::SsruTranslate`（缓存后缀 `-ssru-v3.onnx`，`en_zh-Hans` 图体积由 `117.64 MiB` 降至 `43.82 MiB`），标准 `buildModel(..., false)` 非原生图保持完全不变以兼容 `onnxruntime-web/wasm`。
   - 新增 ragged-batched C++ 本地 `Encoder`（融合 8 路 Decoder context K/V 投影与转置）与连续批处理 `Decoder::decodeBatchStreaming`；跳过 CPU-only SSRU 启动阶段的 `model.onnx` 双重加载并采用 `statSync` 模型目录校验。
2. **微内核与持久化线程池（`PcorePool` + `TeamBarrier`）**：
   - 将矩阵权重重排为 `N x K4` 列并行布局，零拷贝 `packInt8`/`createInt8` 消除 FP32 嵌入常驻副本，x64 提供 zero-spill `6x16` AVX-VNNI 与 AVX-512 VNNI 内核，并将 `AvxVnni`/`Avx512Vnni` CPUID 检测严格绑定 FMA 位；使用 `mlasExpAvx2Fma` 向量化 `ssruGateUpdate`（提速 `4.87x`）。
   - `PcorePool` 拓扑感知 P-core 与超线程 sibling 互不重叠绑核，并在 `PcorePool::runTeam` 回退 `nt == 1` 时跳过多核 `TeamBarrier` 等待/取消，消除多引擎并发死锁；`active >= 4`（或 `total_tokens >= 64`）解锁 `6P+6HT`（12 线程）协同，并在解码团队内融合 `FullVocabQ4::argMaxBatchInTeam`（零堆分配并行扫描与重排）。
3. **混合工作窃取连续批调度（Hybrid Continuous Batcher）**：
   - 将 `addon.cc` 全部 `run` / `runBatch` 请求统一汇入连续批队列，单 P-core `TeamBarrier` 团队处理活跃解码槽位（`maxBatch <= 12`），`Shortlist` 按请求分片/4–6 路切分且不再构造跨槽位并集；空闲 E-core（最多 4 核）在后台异步预编码 queued 输入，当 E-core 全部忙碌且队列积压 `>= 2` 时由 P-core 协同窃取执行。
   - 移除 `src/core/engine.ts` 中的 `BATCH_MICRO_SIZE = 8` 串行微批分块及 `UV_THREADPOOL_SIZE` 人为上限，改进 `Shortlist.fillExtra` 为增量脏字清理与精确基表直拷；在 `src/server/index.ts` 为 `/translate` 与 `/translate/batch` 增加直通 Express 热路径跳过 `tsoa` 校验开销。

## 已评估并否决的方案

| 方案 | 实测表现 | 否决原因 |
| --- | --- | --- |
| 跨槽位并集 `ShortlistTable::argMaxBatch` | `active >= 2` 时并集候选膨胀导致 shortlist 耗时增至 `+144%` | 改为独立 per-slot 与 `active==1`（`>=512`）4–6 路分片并行 |
| `addon.cc` 贪心配对 `fastTask2`（`M=2`） | `TranslationEngine` Fast `c=8` 出现 `-6.6%～-10.3%` 回退 | 同组等待较长句尾拖累且仅占用部分 P-core，改用统一连续批消除回退 |
| `TranslationEngine` `BATCH_MICRO_SIZE = 8` 串行微批 | 长文 `c=1` 产生 `-25%～-29%` 回退 | 人为引入批边界屏障，改为全量句子直传一次连续调度 |
| `TeamBarrier` 自适应 `sched_yield` 自旋 | Linux EEVDF 下出现 `4 ms` 调度切片尖峰（局部跌至 `0.16x`） | 还原纯 `cpuRelax()` 句内有界自旋并严格限制不超物理核+HT 配额 |
| `M=1` 独立工作线程 `ht_first` 12 线程 | P-core L2 互相驱逐，Fast `SHORT c=8` 从 `1792` 跌至 `1225 rps` | 仅在 `active >= 4` / `total_tokens >= 64` 共享批计算时启用 `6P+6HT` |
