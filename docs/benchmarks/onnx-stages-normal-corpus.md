# ONNX 阶段分析与正常请求复测

新发现：原 39 条模型级语料中，两个方向各有一条触及生成上限，输出 244 个 token 且无 EOS。服务在 engine.ts 的 infer 中会把这类结果报为失败。旧模型级计时仍可描述该混合工作负载，但不能称为 39 条全部成功翻译的服务吞吐；后续将正常输入与压力/失败输入分开。

## 方法

- 本机 CPU 单线程、CPU4，普通/快速模式双向。每组先跑两遍未插桩参考，再跑两遍插桩模型，输出逐 token 对照通过；阶段统计仅用第二遍。优化模型与 trace 同一会话生成，所有叶子节点均按名称、算子及数据依赖验证归类，未归类节点会导致断言失败。
- 编码器以 K/V 投影所用的 encoder hidden 为边界；K/V 以 Loop 的外部输入依赖为边界。解码与最终投影按 hidden 和输出 token 的依赖拆分。排除 Loop 和 SequentialExecutor 容器，验证叶子区间不重叠、阶段时间求和与叶子总时一致。
- FFN、注意力、RNN 按原图归一化模块出口追溯优化图依赖；RNN 组包含初始 token embedding/position 准备，剩余末端 Reshape 单独记为 shape。没有把纯算子类型等同于整个架构阶段。
- 重新跑未插桩模型核对输出长度并标注 EOS。37 条正常输入与两条达到生成上限的输入分开；这仍是小型开发输入集，不代表生产流量。

## 测量边界

- 仅占原语料约 5% 的两条失败输入，在不同方向/模式中占叶子计时约 33%–41%，会明显改变总权重。长度分组也保留在 JSON；英译中正常长输入仅一个、中译英正常输入没有 >64 token 组，不能据此画出一般长度规律。
- 本组 profiling 的 JS wall time 为未插桩的约 1.4–3.1 倍，且放大幅度随模式不同。模型运行时间中叶子事件外的约 15%–34% 同时包含调度、分配和 profiling 等开销，不能全部叫作解释器开销，也不能直接当作可优化比例。
- 上表是插桩算子计时组成，不是未插桩服务的占比、硬件周期或加速上限。此轮未测 GPU、多线程 trace 或 HTTP 开销。

## 仅正常请求的短时自旋复测

- 当前原模型、双线程，500 µs 自旋目标、最后一个 Run 结束停止；19/18 条正常输入，六轮交替、每块六遍、1/4 路并发。所有输出均与基线相同且以 EOS 结束。
- 新工作负载未稳健复现原混合集的收益，单请求 CPU 成本继续增加。各轮波动很大；这并未证明“删掉失败输入”是唯一原因，但足以阻止把旧混合集的小幅优势推广为默认配置。
