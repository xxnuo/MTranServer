# 5.4.2 全链路性能优化与候选方案实测报告（2026-11-16）

本报告记录基于 `5.4.1`（提交 `a0ed6c6`）开展的多轮热点剖析、采纳方案、否决方案及跨平台端到端实测结果。全部采纳改动保持逐 token 输出一致：六个目标平台托管运行器（含虚拟机）及四台实体设备均通过 **2049/2049** 条样本（FLORES-200 `devtest` 双向 2024 条 + 基准语料 25 条）逐 token 对照与 EOS 检查，本机扩展验证 **4043/4043** 条样本零差异。原始统计数据保存在同名 [JSON](performance-optimization-2026-11-16.json)。

## 根因剖析

在 `Intel Core i5-14400`（20 MiB L3 缓存）上对 `5.4.1` 的 `SsruDecode` 进行逐阶段纳秒级采样（8 并发、400 条 FLORES 句子、10,446 个生成 token）发现：

1. **L3 缓存抖动与带宽放大**：`Wemb` FP32 词表占 `49.2 MB`（超出 20 MiB L3），且每条请求解码前都会转置分配约 `2.2 MB` 的私有 `w.projection_`（8 并发合计 `17.6 MB`），导致 `shortlist` 单 token 耗时从单并发 `65 us` 飙升 4.8 倍至 `314 us`（占解码总耗时 **36.6%**），并把 `7.08 MB` 共享预打包解码权重不断挤出 L3。
2. **逐 token ORT `InvokeOp` 与分配器竞争**：每生成一个 token 仍调用 24 次 `DynamicQuantizeLinear`、24 次归一化缩放加偏置算子，且每句重分配 `Workspace` 触发堆分配与页表回收（`setup+other` 占 **12.5%**）。
3. **JS/服务层与启动校准开销**：`Shortlist` 每句构造 `Set`、排序及装箱 `BigInt64Array`；`getOrCreateSingleEngine` 在热路径每次请求经 `libuv` 线程池异步读取 `manifest.json`，高并发时与原生推理争用同一线程池；`selectBackend` 在已有原生插件的 Fast CPU 路径仍额外创建约 15 个临时多线程 ORT Session 做无效扫描；批量翻译控制器逐条串行等待；CLI/容器未显式配置 `UV_THREADPOOL_SIZE` 时默认受限于 4 线程。

## 采纳方案

1. **L3 常驻两阶段 INT8 候选表 + 逐行 Cauchy-Schwarz $L_2$ 精确剪枝重排（`ShortlistTable`）**：模型加载时将词表按行对称量化为 `int8`（约 `12.3 MB`，与 `7.08 MB` 解码打包权重合计 `19.38 MB < 20 MB L3`），预计算每行 $L_2$ 范数与量化残差 $L_2$ 范数。第一阶段用 AVX-VNNI、AVX2 拆分无饱和点积或 ARM64 SDOT 扫描候选词并精算最优候选的 FP32 logit；第二阶段利用 Cauchy-Schwarz 严格误差上界剪除 >99% 不可能反超的候选，仅对极少数临界行执行精确 FP32 点积（Apple M4 KleidiAI SME 路径使用与 SME 外积一致的顺序 `std::fma` 累加），省去每句 `w.projection_` 转置拷贝。
2. **原生无锁 `quantizeLinearU8`、寄存器内 `separate_bias` 与 `thread_local` 缓冲复用**：用 SSE2 / NEON / 标量实现与 ORT 1.30 逐位一致的动态量化，合并归一化尾部的乘加循环，无分支化有限性检查，并按线程复用 `Workspace` 与 `Invocation`。
3. **JS 位集合 `Shortlist` 与单遍 `Int32Array` 输出校验**：预计算固定前缀/EOS/byte token 位图，通过 `Math.clz32` 位扫描直接写入 `BigInt64Array` 底层 32 位视图（实测 5,060 句耗时从 `1038 ms` 降至 `74 ms`，提速 **14.0 倍**）；复用 `Intl.Segmenter`，合并输出 token 校验与切片。
4. **服务层热路径与启动优化**：对已稳定落盘的 `manifest.json` 采用 `statSync` 元数据缓存避免占用 `libuv` 线程池；`cacheSize <= 0` 时跳过 `JSON.stringify`；Fast CPU 原生插件可用时跳过冗余多线程 CPU 扫描；入口在未显式设置 `UV_THREADPOOL_SIZE` 时按 `Math.min(16, Math.max(4, availableParallelism()))` 自动初始化线程池；`/translate/batch` 及 `Kiss`/`DeepL`/`Hcfy` 批量接口改为 `Promise.all` 并发调度；GPU 文档加速在完成单请求校准后允许空闲 GPU 并发处理单篇文档并将竞争请求溢出至原生 SSRU CPU。

## 已评估并否决的候选方案

| 候选方案 | 实测表现 | 否决原因与边界 |
| --- | --- | --- |
| 手写 64 列 `j+=4` 广播 AVX-VNNI 内核 (`exp1`) | 8 并发 packed 耗时 `5293 ms`（原 Gemmology 8 列 `k+=32` 为 `3030 ms`） | 外层循环与广播次数增加 8 倍，在混合大小核 CPU 上明显退化 |
| 每句 32 列面板转置 FP32 `w.projection_` (`exp2`) | 8 并发耗时 `2855 ms`（共享 INT8 表仅 `1392 ms`） | 8 份私有 `2.2 MB` 缓冲仍占 `17.6 MB`，持续冲刷 L3 中的解码权重 |
| 标量/FMA 原生 `Attention` 与 `LayerNorm` | 吞吐降至 `183 rps`（基线 `197 rps`），且 2049 条中出现 `17` 与 `68` 条差异 | 慢于 ORT MLAS SIMD，且归约舍入变化跨过后续动态量化边界 |
| 无重排 FP16 / 无重排逐行 INT8 候选表 (`exp5`) | 英→中开发集 `165/997` 条译文变化，`chrF++` 下降 `0.0761` | 两阶段 INT8 + Cauchy-Schwarz 精确 FP32 重排在同等 L3 命中率下实现 `0/4043` 差异 |
| 宽松 Hölder $L_1/L_\infty$ 剪枝界 | 英→中 8 并发从 `321.5 rps` 跌回 `121.0 rps` | 约 31.8 logit 的最坏界几乎放行全部候选行重算 FP32；改为逐行 Cauchy-Schwarz $L_2$ 界（约 0.5 logit）解决 |
| 关闭或收缩 ORT `CpuMemArena` | 关闭 Arena 吞吐下降 `-24.4%`（`347.95 → 262.93 rps`），峰值 RSS 反升至 `376.2 MiB`；开启收缩无内存收益且略降速 | 高频步进分配加剧多线程堆锁竞争与碎片；双份常驻内存需后续通过自定义格式解耦 |
