# 分步解码与投影组批原型

结论：原生 C++ 调度下，两个方向均观察到整句吞吐改善，值得继续验证。尚未接入生产，不把微基准或当前原型当作服务收益保证。

## 原型与正确性

- 将现有模型拆成编码和首步、后续单步解码、投影三个阶段；各请求独立解码，仅把两条请求的投影合并。用现有 ORT 公共 C API，未替换指令分派或修改运行库。
- 直接拆原始图并分别优化时，长输入出现 token 差异；保留原始单请求投影仍会失败。从本机 ORT 已优化图拆分、禁用再次图优化后，测试恢复一致。尚未定位具体哪项图变换造成差异，不能把冻结优化图当作跨平台保证。
- 单请求保留原始投影子图；双请求投影保留 INT4 Top9 后 FP32 精排，改成对应的批量张量运算。请求 EOS 或达到原模型的长度上限后退出，剩余单请求改用原始投影。
- 39 条原始输入双向逐 token 一致。重排配对并加入 8 条短输入、重复 token 等构造用例，共 125 次输入，也通过 Node 和原生 C++ 的完整输出对照；其中包含重复输入，不是 125 条独立语料。
- 原生三方性能对照的 2,808 次计时翻译全部校验输出；计时外另有完整语料预热和基线参考生成。扩展输入检查未报告越界或未定义行为，但 LeakSanitizer 每进程报告 ORT 内同一位置的 14 字节分配未释放。仅加载 ORT 并创建/释放环境、不加载模型的最小程序也能复现；因此不能称为内存检查完全通过。仅测试器经过插桩，ORT 动态库没有。

## 同条件整句对照

同一物理核心、ORT 单线程、相同语料、相同每段请求数量。每方向做八轮正反顺序交替；每段三个完整语料遍历。三个会话方案驻留，但一次只运行一个方案。测试机不是独占环境，区间反映实际波动。

| 方向 | 候选相对完整 Loop | 吞吐变化中位数 | 八轮变化范围 | 加速轮数 |
|---|---|---:|---:|---:|
| en_zh-Hans | 仅拆分，batch=1 | -2.8% | -18.4% 至 +5.5% | 2/8 |
| en_zh-Hans | 拆分并组批，batch=2 | +10.2% | +3.4% 至 +16.2% | 8/8 |
| zh-Hans_en | 仅拆分，batch=1 | +2.9% | -22.0% 至 +7.1% | 6/8 |
| zh-Hans_en | 拆分并组批，batch=2 | +21.6% | -12.2% 至 +27.8% | 7/8 |

- 只拆分没有稳定净收益；在两方向的全部八轮中，batch=2 都优于同轮的 batch=1。
- 较早的原生两方对照中，batch=2 相对完整 Loop 的中位数约 +12.7% / +18.0%，各八轮均加速。三方复测中，中译英出现一轮退化，不隐去该结果。
- Node 长测的中位数约 +0.4% / +14.0%，英文仅四轮加速。提示调度/接口开销需要单独评估，不能直接套用投影约两倍的微基准。
- Node 长测期间曾编译测试器，有额外主机负载，因此该组只作为辅助证据。原生计时期间未并行运行其它本任务基准或编译；系统其它负载仍存在。

## 未完成的采用门槛

1. 当前按固定两请求一组处理，不在短请求结束时立即交付或填入新请求。需要连续组批调度、等待超时以及低负载直接走完整模型的策略。
2. 尚未验证 HTTP 实际请求、p95/首响应延迟、取消、异常清理、共享会话多线程压力、内存峰值和长时间稳定性。额外会话/权重的内存代价未量化。
3. 需要可维护且跨机器可验证的分步图生成方法；本机导出的优化图可能带硬件相关变换。其他 CPU、语言对和更广语料均未验证。
4. 全部已测 token 相同仍不能证明所有输入数值等价。正式采用必须保留原路径，并验证分步后的缓存/会话生命周期及取消边界。

生产源码、模型制品和版本未修改，未触发构建发布。下一阶段优先补连续组批及延迟测试，而不是直接更换默认后端。
