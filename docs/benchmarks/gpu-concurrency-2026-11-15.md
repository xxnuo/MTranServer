# CPU / GPU 并发吞吐：普通、Fast 与 LinguaSpark

2026-11-15 实测。GPU 队列能够提高长文并发吞吐，但当前默认策略在请求竞争时主要使用 CPU，不能把实验队列的收益算作默认版收益。LinguaSpark 在中译英长文和短句吞吐上仍领先。

## 测试条件

- MTranServer 5.2.1，基于提交 `3a02b390e6c1f22f1a3c500dc173d72398f45cfa`；普通和 Fast 的 CPU 路径均为 native-async。GPU 使用 MLX 0.32.4，Apple M4 为 Metal，NVIDIA Thor 为 CUDA SM110。实验使用的 GPU worker 和运行库与构建产物哈希一致。
- 两台设备均使用原生进程，逐个运行各方案，调度优先级 nice 15，不设置 CPU 配额或独占核心。M4 使用 Node 26.13.0，Thor 使用 Node 22.23.5；只做同机方案对比，不用跨机器的绝对耗时判断硬件优劣。
- LinguaSpark server 固定版本 `edd16a674b1484490a4a29d588dab9c1a191e6c3`，引擎固定版本 `269605c`，仅支持 CPU；M4 为 10 个 worker，Thor 为 14 个 worker。
- 三方使用相同来源的 Mozilla 中英双向模型，已核对各模式和两台设备的原始模型 SHA256；20 条短句与两条 32 句长文，混合场景等量交替发送两个方向的长文。
- 关闭翻译结果缓存，预热模型及 GPU 内核，再轮换方案顺序跑三轮。单方向长文测 1、4、8 并发，每轮分别 6、24、32 次；混合长文测 4、8 并发，每轮各 32 次；短句测 8 并发，每方向每轮 120 次。每台 8988 次，共 17976 次正式 HTTP 翻译请求，无失败。
- 吞吐、延迟均包含 HTTP 及排队开销；下表取三轮对应指标的中位数，P95 为每轮最近秩百分位数再取中位数。CPU 自动调参可能在不同进程间选择不同线程数，默认策略的变化不能全部归因于 GPU。
- **CPU**：显式关闭 GPU。**默认策略**：保持生产版的并发准入与校准。**GPU 队列**：临时放开竞争请求的 GPU 准入并强制选择已有 GPU 路径，沿用单文档句子批处理，不增加跨请求组批；所有计时长文请求均由实际 GPU 调用计数确认，无 CPU 回退。

## 8 并发长文吞吐

单位请求/秒，越高越好。GPU 队列为实验方案，尚未合入默认策略。

| 设备 | 场景 | 普通 CPU | 普通 GPU 队列 | Fast CPU | Fast GPU 队列 | LinguaSpark CPU |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| M4 | 英→中 | 8.38 | 10.32 | 10.06 | **11.81** | 11.00 |
| M4 | 中→英 | 4.55 | 5.41 | 7.30 | 8.72 | **12.93** |
| M4 | 双向混合 | 5.39 | 8.78 | 8.26 | **12.91** | 11.82 |
| Thor | 英→中 | 5.58 | 6.39 | 6.90 | 7.37 | **8.66** |
| Thor | 中→英 | 2.76 | 3.41 | 4.98 | 5.64 | **9.90** |
| Thor | 双向混合 | 3.59 | 4.90 | 5.88 | 8.05 | **8.99** |

Fast 双向混合长文的 GPU 队列吞吐相对 CPU：M4 提高 **56%**，Thor 提高 **37%**；普通模式分别提高约 **63%**、**37%**。这不表示 GPU 在所有方向或尾延迟上都领先。

## 默认策略与实验队列的区别

8 并发双向混合长文，单位请求/秒。

| 设备 | 模式 | CPU | 默认策略 | GPU 队列 |
| --- | --- | ---: | ---: | ---: |
| M4 | 普通 | 5.39 | 5.59 | **8.78** |
| M4 | Fast | 8.26 | 8.59 | **12.91** |
| Thor | 普通 | 3.59 | 4.26 | **4.90** |
| Thor | Fast | 5.88 | 6.26 | **8.05** |

汇总单方向及双向混合的 8 并发长文场景，每台设备的默认策略合计只有 **24 / 576（4.17%）** 请求实际使用 GPU，其余约 **96%** 使用 CPU。单方向每组为 3 / 96，双向混合每组为 6 / 96；不能将“允许 GPU”与“所有并发请求走 GPU”混为一谈。

## 范围与记录

- 本次只测热态吞吐，未测冷启动、长期压测或其它语言；两个固定长文不代表所有实际流量。GPU 计时包含现有工作进程回收的成本。
- 每次输出均与该模式已知的 CPU 或 GPU 参考结果核对；通过检查不表示 CPU、GPU 和 LinguaSpark 译文相同，也不表示翻译质量等价。本次未重新做独立质量评估。
- 仅测试并记录，未修改生产策略、发布或部署服务；临时测试入口和运行进程已清理。
- 完整的 1/4/8 并发结果、逐轮耗时、P95、进程树 RSS 和实际 GPU 请求计数保留在本地 `.tmp/gpu-concurrency-20261115/`：汇总为 `summary.json`，原始结果为 `m4-results.json` 和 `thor-results.json`。临时源码、模型、机器路径与日志不上传。
