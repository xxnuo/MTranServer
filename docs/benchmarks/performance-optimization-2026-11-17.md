# 5.4.3 普通与 Fast 双模式性能优化及候选方案报告（2026-11-17）

本报告记录在 `5.4.2`（提交 `fa5fc48`）基础上针对普通模式（`--no-fast`）与 Fast 模式（`--fast`）开展的深度剖析、采纳方案、否决方案与跨平台验收结果。六个目标平台托管运行器（含虚拟机）及四台实体设备均通过 **4,098 / 4,098** 条样本（Fast 2,049 条 + 普通模式 2,049 条，每模式含 FLORES-200 `devtest` 双向 2,024 条与基准语料 25 条）逐 token 一致与 EOS 验收。结构化数据见 [performance-optimization-2026-11-17.json](performance-optimization-2026-11-17.json)，与 LinguaSpark 的同口径 HTTP 对照见 [cpu-comparison-2026-11-17.md](cpu-comparison-2026-11-17.md)。

## 根因剖析

1. **普通模式仍停留在原图 `Loop` + 15 次启动线程扫描**：`5.4.2` 中普通模式（`shortlist = false`）未接入原生 `SsruDecode`，每步解码仍走 ORT `Loop` 子图调度与 `MatMulNBits` + `TopK(9)` + `Gather` + `MatMul` 算子链，且启动校准阶段执行约 15 轮 CPU 线程数扫描，导致热缓存启动耗时高达 `4.38 s`（`i5-14400` 上达 `20.9 s`），长文与并发吞吐显著落后于 Fast。
2. **`SsruDecode` 逐步 `OrtValue*` 包装分配与双线性重复量化**：解码每步为 `Sigmoid`、`InstanceNormalization`、`Sin`、`Attention` 反复创建与释放 `OrtValue` 张量包装；每层 SSRU 的 `(rnn_Wf, rnn_W)` 对同一激活向量重复执行两次动态量化。
3. **候选表 `0x4101` 精确 INT8 权重与 Stage-2 标量扫描开销**：Mozilla `intgemm` 模型嵌入层本身源于对称 8-bit 量化（约 99.9% 行在对称 `int8` 重建下残差 `dw_l2 == 0`），此前仍按非零残差计算保守上界；Stage-1 尾部标量找次优值与 Stage-2 逐行标量计算亦存在分支与访存冗余。
4. **JS / N-API 热路径装箱与长文重复分词**：每次推理构造 `ort.Tensor` 与拷贝 `BigInt64Array`；`translateText` 在长度判断前无条件调用 SentencePiece 分词，导致长文分句前额外执行一次全文分词。

## 采纳方案

1. **普通模式原生 SSRU 与 `FullVocabQ4` 全词表两阶段投影**：
   - 图构建器支持 `shortlist = false` 时生成空 `candidate_ids` 常量的原生 `com.mtran::SsruDecode` 图（缓存后缀 `-ssru-v2.onnx`），普通模式 CPU 同样跳过启动阶段的多线程扫描。
   - C++ 实现 `FullVocabQ4`（64 元素分块 4-bit 对称权重量化 + Top-9 粗排 + FP32 `dotRow` 精确重排）：x64 提供 AVX-VNNI 8 列展开 `neg_corr` 内核与 AVX2+FMA 4 列内核；ARM64 对齐 ORT 1.30 KleidiAI `qai8dxp_qsi4c32p` 语义（`bf16` 截断块缩放 + 逐行动态量化 + SDOT 8 列展开）；MSVC 显式声明 `#pragma fp_contract(off)` 保证跨编译器浮点舍入一致。
   - 针对单并发请求（`activeRuns <= 1`）提供 4 路工作线程协同扫描，并采用句内短自旋（`cpuRelax`）衔接条件变量休眠，避免混合大小核 CPU 在逐 token `futex` 唤醒时跌入低频能效核，空闲时保持零 CPU 占用。
2. **句级 `SentenceTensors` 复用与 `linearPair` 激活共享量化**：句内固定地址缓冲复用 `OrtValue*` 包装（减少约 99.1% 的逐步张量包装分配）；合并 `(rnn_Wf, rnn_W)` 的 `quantizeLinearU8` 量化；用 SSE2 / NEON 向量化非有限数检查。
3. **`ShortlistTable` 精确 INT8 行识别与 $O(1)$ 提前剪枝**：预检测 `dw_l2 == 0` 的精确 `int8` 词表行，压缩 `RowMeta` 至 16 字节对齐，Stage-1 同步维护次优近似分 `second_logit`，当全部候选误差上界均无法反超时直接跳过 Stage-2 遍历。
4. **零 `ort.Tensor` 的 `runRaw` N-API 通路与预分词快速剪枝**：新增 `session.runRaw` 直接传递类型化数组与标量 EOS；在分词前增加字符长度快检消除长文双重分词，补充无占位符纯文本快路径与小端 `Int32Array` 视图直传。

## 实测收益摘要

### 1. Ryzen 9 9950X 受限容器三引擎 HTTP 对照（4 CPU 配额、3 GiB 内存、三轮中位数）

详见 [cpu-comparison-2026-11-17.md](cpu-comparison-2026-11-17.md)：

- **普通模式（`5.4.2 → 5.4.3`）**：热启动就绪 `4377.4 → 1280.2 ms`（提速 **3.42 倍**）；单请求延迟英→中短句 `4.36 → 2.89 ms`（快于 LinguaSpark `3.75 ms`）、中→英短句 `5.42 → 3.57 ms`、英→中长文 `72.82 → 44.79 ms`（为 LinguaSpark 的 **6.13 倍**）、中→英长文 `132.40 → 91.78 ms`；8 并发短句吞吐 `633.46 → 1147.73 req/s`（**+81.2%**，P95 由 `46.42 ms` 降至 `7.75 ms`）与 `495.04 → 795.65 req/s`（**+60.7%**）；4 并发长文吞吐 `+72.3%` / `+55.9%`。
- **Fast 模式（`5.4.2 → 5.4.3`）**：单请求短句降至 `2.26 / 2.15 ms`，32 句长文降至 `26.63 / 34.61 ms`（为 LinguaSpark 的 **10.30 / 6.23 倍**）；中→英短句 8 并发吞吐由 `2123.60` 提升至 **`2280.10 req/s`**（**+7.4%**，为 LinguaSpark 的 **1.66 倍**）。

## 已评估并否决的候选方案

| 候选方案 | 实测表现 | 否决原因与边界 |
| --- | --- | --- |
| 类 FEXIPRO 词表 SVD 主轴旋转 / 范数剪枝 | 离线 SVD 初始化增加 `>1.8 s` 启动开销与 `98 MB` 额外常驻矩阵；Top-9 粗排阶段仍需访问低秩残差才能保持逐 token 一致 | 对 `dim=384` 全词表扫描，4-bit 对称块量化（`12.5 MB`）的顺序带宽已低于主轴投影 + 残差上界两遍访存，且破坏启动速度与内存目标 |
| `FullVocabQ4` 16 列寄存器展开 AVX-VNNI 内核 | 16 个累加器超出 16 个 YMM 寄存器上限触发栈溢出（register spill），单步扫描反慢约 `9%–14%` | 保留 8 列（2 组 × 4 列）展开，恰好常驻 8 个累加器 + 4 个激活寄存器 + 掩码/偏置寄存器 |
| 编码器 QKV / KV 合并后 `Split` 跨步拷贝 | 图重写后因 ORT `Split` 产生非连续列块拷贝，短句与长文端到端延迟无净收益（波动 `-2%`～`+0.5%`） | 编码器与 K/V 合计已不足总推理耗时的 15%，额外张量重排抵消了少量算子调度节省 |
| `FullVocabQ4` 逐 token 无自旋 `condition_variable` 唤醒 | 在混合大小核 `i5-14400`（`powersave`）上单并发短句 P95 退化至 `61.9 ms`（吞吐 `-31.1%`） | 逐 token `futex` 休眠导致辅助线程频繁迁移至低频 E 核；改为句内有界 `cpuRelax` 自旋后 `SHORT_EN c=1` 升至 `93.6 req/s`（P95 `14.2 ms`）、`PARA_EN c=1` 升至 `30.5 req/s` |
