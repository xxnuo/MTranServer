# ORT 映射存储及外置 embedding 复测

结论：暂不改默认模型存储。ORT 映射并直接引用权重明显减少初始化时间和峰值内存，但短块推理测试出现回退、延长复测差距缩小，尚未证明吞吐无损；映射后复制权重增加初始化峰值。外置 embedding 的延长复测接近基线，还不能视为已验证的通用优化。

## 方法与统计修正

- Linux x64、ORT 1.30.0，本机 CPU 固定在 4/6/8/10；没有跨硬件结论。内存测试每次独立 Node 进程，线程数 1，正反顺序各两次。页缓存已热，RSS 包含 Node；不可与此前纯 C++ 进程的绝对 RSS 直接比较。
- 使用两个方向、普通/快速模式及原 39 条输入。持续测试每个配置四轮交替，1/2 个 ORT 线程、1/4 路并发，每块六遍完整语料。一个块仅存活一个会话，先完整预热。
- 旧临时脚本的 `tokens += await run(...)` 会在并发时覆盖计数；已改为等待返回后同步累加，并断言总 token 数。旧脚本的逐 token 输出断言、固定请求数及计时仍有效，但旧 token 总数不能用于吞吐计算。本记录的新数据都使用修正后的脚本。
- 下表吞吐变化为每轮“原 ONNX 耗时 / 候选耗时 - 1”的中位数；正数表示候选更快。CPU 时间用于辅助检查，逐轮原始值保留在 JSON。
- 使用 ORT 公共保存/加载接口，实验 addon 仅增加 `session.use_memory_mapped_ort_model` 和 `session.use_ort_model_bytes_for_initializers`；未修改内核或生产源码。进程 maps 已观察到实际 `.ort` 映射。

## 针对性复测

- 英文快速模式、单线程、四路并发，六轮交替，每块 24 遍完整语料；两种候选分别和原 ONNX 比较，并非同一轮三方随机实验，不能据此完全定位退化原因。
- 映射直接引用权重：配对中位吞吐 -0.78%，CPU 效率 -1.00%。所有输出及 token 总数断言通过。
- 映射后复制权重：配对中位吞吐 +1.84%，CPU 效率 +1.89%。所有输出及 token 总数断言通过。
- 直接引用权重在该场景从短块约 -4.19% 缩小到长块约 -0.78%，不能把短块退化幅度当作稳定结论，也不能据此推断其他配置均无退化。
- 复制方式四组初始化约 98–129 ms，但峰值约 364–439 MiB，对照约 251–312 MiB。普通 `.ort` 加载也增加峰值；不能把更快启动说成没有内存代价。
- 中文普通模式、双线程四路并发的 embedding 外置延长复测为 5,472 次翻译，吞吐约 +0.70%，CPU 效率约 +0.56%。此前约 2% 的回退未重现，因此结论改为此场景近似持平，尚未补全四组矩阵及内存测试。

## 采用边界和下一步

- 先保留当前生产格式。后续已完成 embedding-only 双向双模式矩阵及扩展输入驻留实验：常驻内存优势在更分散输入后基本消失，详见 [外置 embedding 复测](embedding-external-residency.md)。
- ORT 保存时明确提示优化产物可能包含硬件相关变换。若采用，需本机生成并按 ORT/硬件失效重建，保留原模型回退；不能直接作为跨平台分发包。
- 未测冷盘、全词表页面驻留、完整 HTTP 服务启动、更多语言/长文本、其他 CPU/系统，也未完成缓存原子发布、损坏恢复及取消/重启验收。未进行这一新格式的 sanitizer 检查。
- 未改生产源码、版本或构建产物。本轮是探索记录，不是已上线优化；目标仍继续。
- 本地复现脚本和模型在 `.tmp/ort-storage/`，外置实验在 `.tmp/external-embeddings/`；JSON 保留源模型和脚本哈希及完整原始数据。没有上传完整可移植实验包。
